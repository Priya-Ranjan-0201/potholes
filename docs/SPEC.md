# PART B — SPECIFICATION (docs/SPEC.md)

## B1. Mission
ScamRoad turns any camera-equipped vehicle or inspector into a road-condition sensor. The edge device detects and tracks potholes (and, as data allows, cracks and other damage) in real time, assigns each physical defect one persistent identity, geotags it, and syncs verified evidence to a backend that deduplicates across devices and time, maps it, scores severity, generates work orders, verifies repairs and reports analytics. Citizens can also report via phone.

Roles: Citizen, Inspector/Driver (edge operator), Maintenance Manager, Contractor, Admin.

## B2. Taxonomy (single source: `shared/taxonomy.yaml`)
Fields per class: `id, code, name{en,hi,pa}, group, status{TRAINED|LIMITED_DATA|NOT_AVAILABLE|EXPERIMENTAL}, detector, color, severity_base`.

Tier 1 (build first, must reach production quality): `POTHOLE`.
Tier 2 (from RDD2022 labels): `CRACK_LONG (D00)`, `CRACK_TRANS (D10)`, `CRACK_ALLIGATOR (D20)`.
Tier 3 (only if labelled data is collected and evaluated): `WATERLOGGING, MANHOLE_DAMAGED, MARKING_FADED, SPEEDBREAKER_DAMAGED, EDGE_DAMAGE, SURFACE_DETERIORATION, SHOULDER_DETERIORATION`.
Tier 4 (experimental/hook only): `RUTTING, UNEVEN_SURFACE` (need depth/IMU data).

After the Phase 2 dataset audit, set each class's `status` from measured evidence. Only `TRAINED` classes are enabled in default inference. Never claim detection for any other class.

## B3. Training pipeline (reproducible)
1. **Data audit** (`ml/data/audit.py`): per-class counts, image size distribution, duplicates (perceptual hash + exact hash), corrupt files, label-format errors, box-size distribution, per-country/source breakdown, leakage check. Outputs `ml/runs/audit/*.json` and a generated `docs/DATASET_AUDIT.md`.
2. **Label unification** (`ml/data/convert.py`): map every source to `taxonomy.yaml`; log every mapping decision; RDD2022 Pascal VOC XML → YOLO format with clamped/validated boxes; drop and log invalid boxes.
3. **Splits** by *location/sequence/source group*, never random frames; fixed seed; stratify by class and country; hold out a **test set that is never used for tuning**; hold out a **local-domain test set** (your own Punjab/Ludhiana images) once collected. Leakage test must pass.
4. **Training:** YOLO nano/small first (edge target); log hyperparameters, git SHA, dataset hash, hardware, duration. Ablations required for: image size (e.g., 480/640), augmentation set, mosaic on/off, low-light enhancement on/off, pretrained COCO vs scratch. Compare with a larger YOLO and RT-DETR on server for reference only.
5. **Hard-negative mining:** run the model on negative-only and validation sets; collect false positives (shadows, patches, stains, puddles, markings, manholes); add as background images with empty labels; retrain; report precision change.
6. **Evaluation (generated by script, never hand-typed):** precision, recall, F1, mAP@50, mAP@50–95 per class and overall; PR curves; confusion matrix; per-country and per-condition (night/rain/blur where metadata exists) breakdown; small-object recall; error gallery; calibration of confidence (reliability diagram); false positives per km on video test sets. Outputs `ml/runs/<id>/metrics.json` → `docs/AI_EVALUATION.md`.
7. **Segmentation (pothole first):** YOLO-Seg using public masks plus your own annotations; report IoU/Dice; used for relative area and road-coverage percent. Crack thinness may justify U-Net — adopt only with measured benefit.
8. **Model card** per exported model: data, metrics, limits, intended use, failure modes, quantization deltas, device benchmarks.

## B4. Edge deployment (core differentiator)
Targets (support those you can actually test; mark others UNTESTED in docs):
- **Android phone** (primary): dev-client Expo app with native inference (ONNX Runtime Mobile or TFLite, NNAPI/GPU delegate where available). Target: OPPO K13.
- **Raspberry Pi 5 / Pi 4** with camera and USB/serial GPS: ONNX Runtime or NCNN, INT8 (UNTESTED until hardware present).
- **NVIDIA Jetson** (if hardware available): TensorRT FP16/INT8 (UNTESTED until hardware present).
- **Laptop/webcam** reference runtime for development and demos.

Edge agent pipeline: `capture → quality gate (blur/exposure) → ROI crop of road region → inference → NMS → tracker → defect consolidation → privacy blur → geotag (GPS + speed + heading + accuracy) → best-frame selection → local outbox (SQLite WAL) → sync`.
Requirements:
- Frame skipping and adaptive `imgsz` to hold a target FPS; never block capture.
- Export script producing FP32/FP16/INT8 models; **INT8 uses a representative calibration set from real data**; report mAP drop and latency per device in `edge/benchmarks/results/*.json` produced by `make bench` on the actual device.
- Metrics reported honestly: end-to-end FPS, inference ms (p50/p95), CPU/GPU/RAM, temperature, battery drain per hour (phone), model size.
- Offline-first: works with zero connectivity for days; outbox with status (`PENDING, UPLOADING, DONE, FAILED`), resumable uploads, idempotency keys, exponential backoff, storage quota/eviction, tamper-evident hash chain of records.
- Device identity: enrollment code → device key; heartbeat; remote config (thresholds, model version) pulled when online; staged model rollout with rollback.
- GPS: record fix accuracy, speed, heading; smooth with a Kalman filter or similar documented method; discard fixes above an accuracy threshold; snap to road segment server-side. Camera-to-GPS offset documented, not guessed.
- Drive mode: no interaction required; audible/visual alert for potholes ahead only with measured latency and a documented false-alarm rate; label as advisory.

## B5. Tracking and deduplication (the "one pothole = one record" guarantee)
Three levels, each with tests:
1. **In-video tracking:** ByteTrack/BoT-SORT IDs per stream, with ego-motion-aware gating (vehicle moves forward; boxes grow and shift downward).
2. **Track → physical defect:** consolidate a track into one `defect_candidate`: best frame by (quality × confidence × area), median of per-frame measurements, track length, frames seen, min/max confidence. Reject tracks shorter than a configurable minimum (documented false-positive filter).
3. **Cross-pass / cross-device / citizen dedup (server):** candidate match score from PostGIS distance (`ST_DWithin` with radius = f(GPS accuracy), not a fixed constant), same road segment, class family, image-embedding or pHash similarity, heading (side of road), time window. Auto-merge above a high threshold; queue for human review in a middle band; separate otherwise. All merges reversible; log in `defect_merge_log` with reasons and scores.

Data model: `defects` (canonical) ← `defect_observations` (immutable, one per sighting). Never overwrite observations. Compute `first_seen, last_seen, times_seen, status`.

Evaluation of tracking/dedup: build a labelled test video set (your own drives, annotated with CVAT) and report ID switches, fragmentation, duplicate rate, merge precision/recall from real data only.

## B6. Severity engine (hybrid, configurable)
`severity_weights.yaml` (versioned). `raw = Σ w_i f_i` over available factors; `score = 100·raw/Σ w_i(avail)`. Levels: 0–25 Minor, 26–50 Moderate, 51–75 Severe, 76–100 Critical. Factors: class base risk, relative area (pothole mask % of road), count/density in segment, lane position if available, recurrence, progression across observations, traffic exposure (only with data), vulnerable-user POIs (OSM schools/hospitals), recent rainfall, speed limit if known. Output: score, level, per-factor breakdown (value/weight/contribution/available), `missing_factors`, `uncertainty_note`, `needs_human_review` (set on low confidence/quality, never silently lowers the score), recommended action and SLA. Human override = new row (`source=human`, reason, user); original kept. Unit tests: each factor, missing-factor renormalisation, golden cases, monotonicity. If human severity labels exist, report agreement (Cohen's κ, MAE) from real data.

## B7. Backend
Services: auth, devices, ingestion (batch sync with idempotency), media, defects, tracking merge, roads/segments (OSM import + snapping), map queries (bbox, clusters via `ST_ClusterDBSCAN`, heat aggregates, geofence, nearest team), complaints (state machine), work orders (SLA timers), repair verification, health index, analytics, forecasting, weather, notifications, reports, admin, model registry (+ staged rollout), metrics.

Complaint state machine (invalid transitions rejected, all logged): `SUBMITTED → UNDER_REVIEW → VERIFIED → ASSIGNED → IN_PROGRESS → RESOLVED`; `REJECTED` from `UNDER_REVIEW|VERIFIED` with reason; `RESOLVED` needs human-verified evidence.

Tables (minimum): users, roles, user_roles, devices, device_heartbeats, departments, districts, wards, contractors, roads, road_segments, inspections, media, model_versions, detections, segmentation_masks, measurements, defects, defect_observations, defect_merge_log, severity_assessments, road_health_scores, citizen_reports, complaints, complaint_status_history, complaint_upvotes, work_orders, work_order_history, repair_records, repair_verifications, weather_records, forecasts, notifications, notification_rules, report_jobs, budget_allocations, sla_policies, audit_logs, system_settings. Demo rows carry `is_demo=true` and the UI shows a "DEMO DATA" banner.

## B8. Maps, health index, forecasting, weather
- OSM base map and road import (document attribution); snapping with `ST_ClosestPoint`/`ST_DWithin`; reverse geocoding through a rate-limit-safe, cached provider; hotspot method chosen and documented (KDE or Getis-Ord); inspector route optimisation with OR-Tools/OSRM when available, fallback heuristic labelled as such.
- **ScamRoad Health Index (project methodology, not an official standard):** per segment/period `100 − min(100, Σ severity_weight × normalised density)`, bands configurable, components stored with method version, length-weighted rollups; segments with insufficient coverage show "Not enough data".
- **Forecasting** only on real accumulated history; baselines (naive, linear) before XGBoost/RF; time-based CV; MAE/RMSE/MAPE and intervals; `INSUFFICIENT_DATA` path tested; UI separates observed vs forecast; budget planning uses transparent configured unit costs.
- **Weather:** pluggable provider (e.g., Open-Meteo; verify terms), cached, graceful "unavailable" state.

## B9. Maintenance and repair verification
Work orders generated from defects (AI-suggested priority, method, SLA, cost from configurable rate card); manager approve/modify with stored diff; assignment; deadlines; SLA timers and escalation; progress photos; contractor metrics from real records. Before/after: match same location, re-run detection, compute damage reduction (relative), flag residual; store as `ai_suggestion`, require `human_decision`. Recurrence monitoring links new defects near repaired ones. Citizen can confirm/dispute.

## B10. Notifications and reports
Rules engine → channels: in-app, email (SMTP), push (Expo), SMS/WhatsApp adapters enabled only with real credentials (else `CHANNEL_DISABLED` with fallback). De-duplicate and rate-limit. PDF/Excel/CSV from DB only, labelled "Estimated" vs "Verified", with data-as-of, filters, model/method versions. AI summary text built from a structured payload; a unit test asserts every number in a summary exists in the payload.

## B11. Web, mobile and edge UIs
**Web:** landing (tagline here only), auth, role dashboards, upload inspection (image/video), result viewer (original vs annotated slider, masks, severity breakdown), live device monitor (heartbeats, FPS, queue depth, model version), map (severity markers, clusters, heatmap, geofence, segment popups, defect history timeline), defect detail (all observations, merges, audit), complaints, maintenance kanban, repair verification, health index, forecasts, analytics, reports, notification center, users/roles, device management (enroll/revoke/rollout), model management (versions, metrics, activate/rollback with confirm), settings, audit log.
**Mobile (Android-first):** auth; Citizen mode (photo/video report with GPS + manual pin, status tracking, upvote, repair confirm); Inspector/Drive mode (continuous on-device detection + tracking, hands-free, outbox status, offline map cache optional); QR segment identification; checklists; notifications; en/hi/pa. Test on at least two emulated screen sizes and one real device (OPPO K13).
**Edge console:** CLI + minimal local web page for status, config, outbox, benchmark.

## B12. Testing matrix
ML: leakage test, determinism test, inference contract (JSON schema), quantization accuracy-drop test, latency bench, quality-gate unit tests, tracking/dedup metrics on labelled videos. Backend: pytest with real Postgres/PostGIS containers, RBAC matrix, upload-security (polyglot, oversized, wrong MIME), rate limits, state machine, migration up/down, spatial tests on known geometries, idempotency tests (replay same upload ×N → exactly one record). Edge: outbox crash-recovery test (kill -9 mid-upload), offline→online sync, clock-skew test, GPS-loss test. Web: Vitest + Playwright E2E. Mobile: Jest + offline-sync scenarios. Security: bandit, pip-audit, npm audit, OWASP ZAP baseline. CI on GitHub Actions with real coverage reports.
